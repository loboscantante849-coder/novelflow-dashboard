# Social Console Slim PRD

版本：2026-08-26  
范围：仅 `https://social.novelflow.top/` 素材生成控制台  
明确不改：`novelflow.top` 主站、书城、用户端、主站 API

## 1. 背景与目标

当前素材站的生产能力已经覆盖 P0-P7、实时榜单、视频、海报、归因和 SocialEcho 草稿，但控制台把“生产操作台、历史复盘、广告分析、AI 助手、策划队列、素材详情”全部塞进一个首屏应用，导致首次打开慢、接口并发多、局部失败影响整体可用。

本次目标不是重写生产链路，而是对控制台做断舍离：保留可恢复、可审计、可评测的生产 Harness；把非生产能力移出首屏；让用户在 3 秒内看到可操作的生产入口，在后台慢慢补齐数据。

## 2. 用户与核心任务

唯一核心用户是运营人员，核心任务按优先级排序：

1. 查看今天是否可生产、今日视频额度、在线账号。
2. 按“应用 × 平台 × 账号”读取实时榜单并选书。
3. 一键创建指定数量素材任务，观察 P0-P7 状态。
4. 将完成素材保存为 SocialEcho `status:0` 草稿。
5. 对失败、等待、歧义任务恢复或停止。

下列能力不属于首屏任务：广告数据、周报、Code/Link 深度分析、AI 策划队列、历史长列表、海报全量预览、完整章节详情。

## 3. 产品原则

- 生产优先：首屏只服务“选书 → 生成 → 草稿”。
- 数据新鲜度优先：实时榜单失败时明确显示不可用，不把历史数据伪装成今日数据。
- 任务可恢复：每个外部 task ID 先持久化，再轮询；歧义任务不自动重试。
- 低耦合：素材站可以独立降级，不影响 `novelflow.top`。
- 默认不正式发布：SocialEcho 永远发送 `status:0`。
- 擦边/露骨不是自动否决条件；唯一硬性开场否决是“醒来、睁眼、起床、闹钟/晨间 routine 作为第一镜头”。露骨风险仍需遵守目标平台和服务商实际审核规则，但不在业务预检中一刀切删除。

## 4. 范围拆分

### 4.1 保留在首屏的 P0-P7 Harness

| 模块 | 首屏职责 |
|---|---|
| 能力条 | 登录状态、存储、LLM、AC、IIIT、SocialEcho、今日额度 |
| 快速生产 | 目标应用、平台、账号、数量、语言、书籍策略、模型策略 |
| 实时选书 | 单一目标路由的榜单、阅读基数/首读率/长读留存/趋势、数据时间戳 |
| 任务列表 | 最近任务的阶段、状态、失败原因、恢复按钮 |
| 草稿结果 | 已创建草稿数量、账号、平台、SocialEcho 状态 |

### 4.2 延迟加载模块

- 任务详情：点击任务后再加载完整证据、文案、视频和海报。
- 历史任务：点击“加载更多”后分页读取。
- 广告数据、周报、Code/Link 查询：独立路由/独立 JS chunk，不参与首页启动。
- AI 策划：显式点击后创建 job，不在首页自动触发。

### 4.3 删除或隐藏

- 删除首页自动轮播、自动展开的长文案、全量海报预览。
- 删除首页同时加载 50 本封面；榜单先无图渲染，视口内再加载封面。
- 删除“多个备用模型”下拉框，改成一个自适应策略；高级模式才显示三模型状态。
- 删除前端对所有任务的高频轮询，改成服务端摘要 + 增量事件。

## 5. 首屏信息架构

```text
素材控制台
├─ 顶部：连接状态 / 今日额度 / 运行中任务 / 草稿数
├─ 主操作：选择目标路由 → 实时榜单 → 选书 → 生成
├─ 任务流：P0 P1 P2 P3 P3.5 P4 P5 P6 P7
└─ 延迟模块：详情、复盘、广告数据、周报
```

首屏只允许一次轻量初始化请求：`/api/console/bootstrap`，返回能力摘要、账号摘要、今日额度、最近 12 个任务摘要和榜单缓存元数据；实时榜单由用户选择目标路由后再请求。

## 6. 选书产品规则

选书上下文必须绑定完整四元组：`applicationId + platform + accountId + language`。不得先取一个跨平台总榜再在前端猜测归属。

默认排序：

1. 周期阅读用户基数。
2. 首读率。
3. 20w 长读留存，无 20w 时使用 10w。
4. 7 天与 30 天趋势。

每个榜单响应必须带：`generatedAt`、`window`、`sourceHealth`、`dataQuality`、`filters`、`fallbackReason`。超过 15 分钟只能标记 stale，不能标记 healthy。

## 7. 模型策略：三模型并发、自适应

### 7.1 三条逻辑路线

不再把旧的 `deepseek` 逻辑名映射到 `deepseek-v4-flash-0731`。改为三个明确的逻辑模型：

| 逻辑名 | 目标模型 | 用途 |
|---|---|---|
| `deepseek-v4-flash-preview` | TokenDance 上的 DeepSeek V4 Flash Preview | 证据总结、长上下文、复杂创意包 |
| `seed-2.1-turbo` | TokenDance Seed 2.1 Turbo | 视频结构、强动作、稳定 JSON |
| `hy3` | TokenDance HY3 | 快速短文案、修复、低延迟任务 |

真实 provider model 名称全部放环境变量，不写死在前端：

```text
NOVELFLOW_LLM_MODEL_DEEPSEEK_V4_FLASH_PREVIEW=
NOVELFLOW_LLM_MODEL_SEED_2_1_TURBO=seed-2.1-turbo
NOVELFLOW_LLM_MODEL_HY3=hy3
```

### 7.2 自适应分工

- P2 故事证据：优先 DeepSeek Preview；超时/结构失败后，同一任务转 Seed，不回退到旧 0731。
- P3 文案：DeepSeek 与 Seed 并发生成候选；HY3 负责短 JSON 修复和字段补全。
- 视频提示词：Seed 主生成；DeepSeek 做冲突一致性检查；HY3 做格式修复。
- 海报提示词：HY3 生成；DeepSeek 只做角色/场景一致性检查。
- 每次模型切换写入 `modelRoute`、原因、耗时、token、输出校验结果。

### 7.3 并发控制

- 全局 TokenDance gate：按 provider 限制并发。
- 每个 run 最多并行 2 个模型请求，避免一个任务占满额度。
- 全局初始并发 4；连续 3 次成功且 p95 延迟低于阈值时升到 6；出现 429、超时或错误率超过 10% 时降到 2。
- 429 只等待并重试同一路线，不把容量问题误判为模型质量问题。
- 每个请求固定超时、最大 token、最大 repair 次数；禁止无界重试。

## 8. 视频质量策略

允许擦边/露骨内容通过内容预检，不将其作为自动 defect。保留以下硬规则：

- 第一镜头不得是醒来、睁眼、起床、闹钟响、刷手机晨间 routine。
- 第一镜头必须有动作、冲突物、公开压力或明确决定。
- 生成完成后保留视频 task ID、媒体 URL、实际执行参数和 provider 偏差。
- 字幕、人物漂移、事件顺序变化不自动判定为合格；进入“待运营确认”或“拒绝”。

## 9. 性能与可用性方案

### 9.1 前端拆包

- `app.js` 拆为 shell、production、leaderboard、detail、analytics 五个 chunk。
- 替换 350KB 级全量图标库为按需图标或内联 SVG。
- 首屏 CSS 只保留 shell + production，广告/复盘样式路由加载。
- 删掉首页不使用的隐藏 dialog DOM，改为点击后创建。

### 9.2 请求预算

首屏预算：

- 首屏 JS ≤ 180KB gzip。
- 首屏 CSS ≤ 60KB gzip。
- 首屏 API ≤ 2 个请求，p95 ≤ 2 秒。
- 首屏不得请求封面、章节正文、完整运行详情。

### 9.3 后端轻量化

- 新增 `/api/console/bootstrap`，只读 Redis 摘要，不调用外部供应商。
- `/api/status` 默认只返回摘要，完整能力诊断显式点击才执行。
- `/api/runs` 默认只返回摘要字段；详情通过 `/api/runs?id=...&detail=1`。
- 榜单分页和缓存按完整路由键隔离，禁止一次拉取多产品线、多平台。
- 所有长任务进入 durable worker；浏览器关闭不影响任务。

## 10. 可观测性与审计

每个 run 必须能看到：

- P0-P7 当前阶段和下一次尝试时间。
- LLM requested/actual model、route switch reason、latency、token、repair count。
- AC/IIIT task ID、提交时间、轮询状态、是否 ambiguous。
- SocialEcho draft ID、accountId、platform、status。
- 数据榜单 generatedAt、sourceHealth、stale/fallback 原因。

## 11. 验收指标

### P0：可用性

- 冷启动到可点击 ≤ 3 秒（中国大陆与海外各测一次）。
- API 失败不白屏，生产入口仍可用。
- 浏览器刷新/关闭后任务状态可恢复。

### P1：模型

- 三模型可并发运行，任何一次路由切换都有 durable 记录。
- Preview 路线不再发送 0731 模型名。
- 429 不产生重复付费任务。

### P2：内容

- 露骨内容不因内容类型自动阻断。
- 醒来式开头 100% 被阻断或要求重写。
- 每个草稿都能追溯到 exact SKU、章节证据和媒体 task。

### P3：草稿

- SocialEcho 仅产生 `status:0`。
- 账号、平台、Code/link 规则 100% 匹配。
- ambiguous 不重复创建草稿。

## 12. 分阶段交付

### Phase 1：止血（1 天）

- 首页只保留生产模式。
- 禁止首屏自动加载广告数据、周报、全量封面和完整详情。
- API 增加超时、abort、错误占位和 bootstrap 摘要。

### Phase 2：拆分（2-3 天）

- 前端 chunk 化，替换全量图标库。
- 榜单按完整目标路由请求，视口封面懒加载。
- `/api/runs` 摘要/详情分离。

### Phase 3：模型路由（1-2 天）

- 引入三个逻辑模型名和环境变量映射。
- 实现并发 gate、自适应窗口、同路由重试和 durable modelRoute。
- 增加 429、超时、结构失败测试。

### Phase 4：验证（1 天）

- 性能预算测试、P0-P7 回归、SocialEcho status:0 审计。
- 仅部署素材站域名，确认 `novelflow.top` 无变更。

## 13. 非目标

- 不重写 P0-P7 业务协议。
- 不改主站页面、书城、用户端和主站 API。
- 不自动正式发布社媒。
- 不因为“看起来大胆”替代平台真实审核结果。

## 14. 最终判断

现在最应该做的不是继续往后台堆功能，而是把素材站收敛成一个轻量生产控制台：首屏只负责生产，复杂数据按需进入；模型从“单一默认模型”改成三路线并发 Harness；质量规则保留对低信息开场的约束，放开擦边/露骨这一不稳定的主观拦截。这样既能提高可用性，也不会牺牲已经沉淀的可恢复、可审计能力。
